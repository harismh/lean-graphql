FINDINGS
M1 (Medium) The four-combination completion algebra is not connected to any executed path.
   - ListCompletion.completeList works on GraphQL.Plan.Completion. Neither executed path uses
     it:
     - the tenant render completes through Spec.collect and Spec.completeList, and every tenant
       list is [T!]!;
     - ItemsExample.complete returns its List String as one value, with no per-element
       completion.
     So the four combinations are proved for a library function, and S4Proofs exercises them
     only on that function.
   - list_completion_contract also assumes every row satisfies elementSpec P E false, the
     non-null element spec. A row that is legitimately (ok none) in a [T]-list is therefore
     outside the theorem, even though elementsNullable = true should admit it.
   The roadmap asks to "cover all four list/nullability combinations", and its S4 acceptance
   names only the tenant and items instances, so this does not block closure. Fix (small): drop
   the non-null premise, or parameterize it by elementsNullable. Then either route
   ItemsExample through completeList, or state in the status that the four combinations are a
   library result that S5 and S8 must instantiate on an executed schema.
M2 (Medium, S6 preparation) Sat is only specialized to pure drivers.
   - sat_run needs resolve : (call : C) → A call, so permitted_driver_authorized cannot express a
     driver with state, retries or per-call variation, although Sat itself already allows them.
   - My probe's sat_run_state (counter-indexed answers) proves the stateful corollary in five
     lines.
   Add a stateful or monadic runner corollary now, for example over any monad with a per-call
   validity hypothesis. S6's certified handler then does not need to reopen Machine.lean, and
   the status's statement "does not require repeated calls to receive the same permitted
   answer" is backed by an exported theorem. This does not block S4.
L1 (Low) ExecutionSwallowedFault is a spec-level fixture.
   - It shows that ItemsExample.specification rejects .ok none [] for a non-null field.
     swallowed_required_fault_rejected already proves this.
   - No fixture mutates the tenant executor or render itself (for example, rendering a framework
     failure as null at a non-null field, or numbering error indices from unfiltered rows) and
     shows that compiled_fault_contract or a pinned rfl breaks.
   The proofs would break under such a change, so this is a gap in regression evidence, not in
   soundness. Rename the fixture, or add a render-mutation fixture in the style of S3's
   unguardedAdapter.
L2 (Low) ItemsExample is not imported by GraphQL.lean, which imports Interpreter and
   ListCompletion. It builds only through Example.Tenant.S4Proofs. Export it, or say in the
   status that it is example code.
L3 (Low) graphql-tenant runs one fixed typed operation on a fixed snapshot.
   - That matches P1: static typed operations, with no request intake before S5 and S6.
   - Nothing in the status overclaims this. Status L7-10 could add "on fixed fixtures" so that
     "application entry" is not read as a serving endpoint.
L4 (Low, wording) deterministic_execution_contract uses Binding.application as a vehicle.
   - It obtains its EvalSpec postcondition by instantiating compiled_frame_invariant and
     actual_response_eq at Binding.application.
   - It is sound, because the statement mentions no adapter. A one-line comment would explain
     why a specific adapter appears in a generic statement.
NOTE (later slices, not S4)
   - Fault.Post keeps successful answers exactly equal to Contract.Expected over the snapshot.
     That is right for S4. For S6, a real external backend needs a refinement relation between
     the external store and the modeled snapshot before it can claim this postcondition. A
     postcondition annotation is not evidence, as the roadmap already says.
   - The view theorem is deterministic only. Faulting drivers may depend on anything, and no
     claim is made about them; keep it that way.
   - S4b must replace pointwise vectorLoad with a certified batch and prove the call bound.
     graph_contract_execution's vectorLoad case will need a .batch Sat case using `compatible`.

WHAT S4 ESTABLISHES
- One executable entry, Runtime.execute, which graphql-tenant uses (through Runtime.run). It
  interprets the actual compiled graph through the pure Machine, with no fuel.
- Deterministic route: for every request, checked P1 operation and agreeing adapter, the
  response equals EvalSpec and is therefore authorized and conforming. Under SuccessConditions
  it is error-free, and filtering the snapshot to the caller's tenant leaves it unchanged.
- Fault route: for every driver whose answers are exact success or declared framework failure,
  the actual execution's response is AuthorizedResponse and Conforms. The proof uses local
  per-constructor evidence, explicit occurrence positions and derived ownership, with no
  EvalSpec equality.
- A second, tenant-free instance: an items(first:) length bound obtained from the contract
  through the same interpreter Sat theorem, preserved through completion at the selected path.
