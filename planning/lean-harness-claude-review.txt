FAIL-CLOSED AND PROCESS BEHAVIOR
- capture:
  - spawns with setsid, so the child is in its own group;
  - drains stdout and stderr on dedicated tasks;
  - polls against a monotonic deadline.
- On timeout, stopChild sends Child.kill, which signals the whole group for a setsid child.
  If the leader is not reaped within 1 s, it sends `/bin/kill -KILL -- -pgid` and reaps.
  I checked that macOS /bin/kill accepts the `-- -pgid` form.
- If the leader exits while a descendant still holds a pipe, the loop keeps waiting until
  the deadline, throws Timeout, and kills the group. So a pipe-holding descendant fails
  closed rather than hanging. SelfTest covers both shapes (a TERM-ignoring loop, and
  `sleep 20 & exit 0`) and requires completion within 5 s.
- withServer: the readiness deadline is 15 s, an early exit is detected, the group is
  killed in `finally` even when an assertion fails, and logs are written.
- The HTTP client is a separate process, so the parent's 10 s deadline bounds sockets. The
  response is capped at 2 MiB. Content-length and chunked framing are checked independently
  of the server, with duplicate, conflicting, truncated and wrong-length responses
  rejected, and self-tests for those cases.
- No leftover processes after the full --all run.

FINDINGS
MEDIUM
M1 Fixed, non-configurable deadlines can fail a slow but correct run.
   - The full `lake build` inside Check.run and the benchmark and generate paths has a hard
     600 s deadline. Each rejection or generated fixture has 60 s, and each aggregate audit
     180 s.
   - The Python check.py had no deadline on the build or audits; only the two named fixtures
     had 60 s.
   - On a cold clone (fetching LeanIO, then building every decide +kernel module) or a slow
     CI runner, the build could exceed 600 s. The harness would then kill a healthy build and
     report a Timeout.
   - The build output is also buffered until it completes, so no progress is shown for up to
     10 minutes.
   - This is not a correctness problem. Successful runs are unaffected, and on a warm tree
     everything takes about 50 s.
   Recommended: an environment override (for example a timeout scale, or "none" for the
   build), or no deadline for `lake build` with streamed output. Document cold-build
   expectations in Harness/README.md.

LOW
L1 The suite totals "All 30 certified…" and "All 35 legacy…" are fixed strings, not counts of
   executed checks; Python counted them. A future edit that drops a check would still print
   30 or 35. Count the `check` calls, or assert the count.
L2 The source guard keeps Python's blind spots. Attributes not first in a list
   (`@[inline, extern …]`) and `attribute [extern …] f` / `attribute [implemented_by …] f`
   are not caught. This is parity, not a regression, and the docs correctly call it a
   source guard. It is cheap to strengthen: scan for the extern/implemented_by tokens inside
   any attribute list or `attribute [` form.
L3 JSON assertions use Lean.Json, which the server also uses for request decoding. A bug that
   is symmetric between Lean.Json's compress and parse would go unseen. The response side
   uses the project's own proved encoder, so the main exposure is the request envelope. This
   is documented accurately in Harness/README.md and the migration document.
L4 Benchmarks rely on /usr/bin/time, which needs `-v` on Linux. GNU time is not installed by
   default on many Linux distributions. This affects benchmarks only, not the gate.
   Mention the package in Harness/README.md.
L5 Benchmark outputs and historical files.
   - New reports go to .lake/benchmarks/*.json. planning/s4b-call-benchmark.json and
     s2a-benchmark.json are no longer refreshed, and the s4b report drops Python's
     `workload` field and shortens `scope`.
   - s4b-status.adoc:104-105 says the planning JSON is "now available as scripts/check
     --benchmark batch". That reads as if the command writes the planning file.
   Suggested wording: "historical; rerun with … (writes .lake/benchmarks/s4b.json)". The
   measurement values do still match exactly.
L6 Several status documents now attribute historical gate results to `scripts/check`, which
   did not exist when those results were produced with `python3 scripts/check.py`. Examples:
   s6a-status.adoc:68, s6b-status.adoc:79, s6c-status.adoc:46. A short "(then
   scripts/check.py)" or "the validation gate" would keep the record accurate.
L7 Smaller behavioral differences, all acceptable:
   - The legacy nested-fragment 2 s bound now includes the client process's spawn time,
     which is slightly stricter and could flake under heavy load.
   - Legacy requests now carry an Authorization header that Python did not send; this is
     harmless.
   - A pipe-holding descendant costs the full deadline before failing.
L8 Bookkeeping: lean-harness-migration.adoc still says "independent Claude review pending".

TRUST BOUNDARY (accurately stated in Harness/README.md and the migration document)
The harness is ordinary executable Lean, outside the proved core. It relies on:
- POSIX process groups, /bin/kill and /usr/bin/time;
- loopback sockets;
- Lean.Json for assertions;
- Lake and the Lean compiler.
The kernel still checks the application proofs. The harness checks inventories,
diagnostics and native behavior. The migration changes no application proof and adds
nothing from P3.
