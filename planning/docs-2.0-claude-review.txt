VERDICT: APPROVED WITH SMALL EDITS.

  optimization proofs. The trust-boundary table and the "Work in progress" sections are

MEDIUM
M1 "2.0" conflicts with the declared version and with the developer-preview framing.
   - lakefile declares 0.0.1. There has been no 1.0. Both documents call this a
     "developer preview".
   - A reader seeing a "2.0" release will assume a stable major version, which the drafts
     explicitly disclaim.
   - The draft says no version was changed, which is honest. But the title
     "lean-graphql 2.0" will travel without that caveat.
   Before publishing, either:
   - explain the numbering in one line (for example, "2.0 marks the proof-first rewrite;
     1.x was the prototype"), and bump the lakefile version together with the tag; or
   - use a 0.x preview version, for example 0.2.0, which matches "developer preview".
   This is the maintainer's decision. It is not an accuracy defect in the text.

LOW (wording; each is a one-line fix)
L1 Tagline punctuation.
   - The requested tagline was exactly "Proof-oriented GraphQL framework in Lean 4".
   - Both files render it as `*Proof-oriented GraphQL framework in Lean 4.*`: bold, with a
     trailing period.
   Drop the period if exact text matters, for example for a package or repository
   description.
L2 README's first proof example is introduced as "the actual execution theorem".
   - Runtime.run_authorized is about the deterministic, unoptimized runtime with an
     agreeing in-memory adapter.
   - It is not the certified effectful, optimized HTTP path. The preceding paragraph is
     about that path ("carries this evidence through to the response bytes"), so a reader
     may conflate the two.
   Suggested wording: "Here is one link in that chain: the theorem for the deterministic
   in-memory runtime…". Optionally add a pointer to Handler.GoodReply /
   returned_bytes_certified as the end-to-end handler guarantee.
L3 The README lists "permitted resolver faults are covered" just before that example.
   - Faults are covered by the S4 and S6b fault proofs, not by run_authorized.
   Either move the clause after the optimization section's fault paragraph, or say
   "(covered by separate fault-contract proofs)".
L4 The release draft says "65 real HTTP checks".
   - 35 of them exercise the legacy prototype server, and the README says that prototype
     does not inherit the proofs.
   Write "30 certified-route HTTP checks plus 35 legacy regression checks", as the README
   already does.
L5 Optimization scope.
   - "The implemented batching transformation groups repeated Task.project lookups" is
     accurate. But the dispatcher applies it only to the recognized
     projects → tasks → project shape, when a keyed capability is present. Everything else
     runs the unoptimized machine unchanged.
   One clause ("for the recognized nested query shape") would prevent a reader from
   assuming a general query optimizer.
L6 Encoding claim precision (optional).
   - "proved against independent ordered JSON and response-envelope relations" is correct.
   - If space allows: the relation is a grammar, not a decoder round-trip, and grammar
     injectivity is listed as a follow-up in the roadmap.
   Not necessary for a README. It would be fair in the release notes' work-in-progress
   paragraph.
L7 "Proved" row in the coverage table.
   - "checked-plan execution" is vague. Consider "execution of checked plans agrees with the
     independent semantics".
   - "call counts" should read "Machine-call counts", matching the earlier paragraph.
